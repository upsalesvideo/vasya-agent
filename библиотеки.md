# Три библиотеки: порядок работы и разрешение конфликтов

Вася собирает сайт тремя библиотеками. Все три уже стоят как скиллы:

| Библиотека | Где лежит | Что она умеет | Роль у Васи |
|---|---|---|---|
| **UI/UX Pro Max** | `~/.claude/skills/ui-ux-pro-max` | База: 50+ стилей, 161 палитра, 57 пар шрифтов, паттерны лендингов, 99 UX-правил. Поиск через `scripts/search.py` | **Меню решений**: из чего выбирать |
| **Impeccable** | `~/.claude/skills/impeccable` | Законы дизайна (цвет, тема, типографика, layout, запреты, тест «сделал ИИ»), референсы по регистрам, команды `audit` / `polish` / `critique` | **Свод законов и ревьюер**: что можно, что нельзя, что доделать |
| **Design Motion Principles (Эмиль Ковальски)** | `~/.claude/skills/design-motion-principles` | Принципы движения Эмиля Ковальски (+ Якуб Крехел, Джей Томпкинс): частотный гейт, длительности, изинги, рецепты, аудит | **Единственный хозяин движения** |

Принцип, который снимает почти все конфликты:

> **Pro Max предлагает, Impeccable решает, Эмиль двигает.**
> Одна библиотека — одна зона ответственности. Если две библиотеки говорят про одно и то
> же, побеждает та, чья это зона. Пожелания пользователя выше всех трёх (кроме контраста
> и доступности).

Ни одна из библиотек не проводит своё интервью. Интервью одно — Васино. Его результат
(`PRODUCT.md` + утверждённая `структура.md`) заменяет и `impeccable teach`, и
`impeccable shape`, и «Light Discovery» у Motion. Второй раз спрашивать пользователя то же
самое запрещено.

## Этап A. Контекст (Вася)

После интервью пишешь `PRODUCT.md` проекта по `шаблоны/PRODUCT.md`. Обязательно поле
`## Register` со значением **brand** (сайт продаёт, дизайн здесь и есть продукт).
Разделы: Product Purpose, Users, Tone, Strategic Principles, Anti-References, Known Gaps.

Проверка, что impeccable его увидит (loader читает папку проекта, не cwd):

```bash
IMPECCABLE_CONTEXT_DIR="<vasya>/сайты/<slug>" node ~/.claude/skills/impeccable/scripts/load-context.mjs
```

В ответе `hasProduct: true`. Если `false` — путь неверный, дальше не идёшь.

---

**Если магазин.** В `PRODUCT.md` регистр остаётся **brand** (витрина продаёт), но
добавляешь строку: «Админка `/admin` — регистр **product**: дизайн служит работе владельца».
При сборке витрины читаешь `reference/brand.md`, при сборке админки —
`reference/product.md` (таблицы, формы, состояния, плотность). Палитра и шрифты у обоих
одни, из `DESIGN.md`; в админке акцент только на действиях «сохранить / удалить»,
без hero-приёмов.

## Этап B. Меню решений (UI/UX Pro Max)

Одна команда даёт дизайн-систему целиком: паттерн лендинга, стиль, палитру, пару шрифтов,
ключевые эффекты, анти-паттерны, чек-лист. Запрос — по-английски, из брифа: тип продукта,
ниша, 2–4 слова настроения из пожеланий пользователя.

```bash
cd ~/.claude/skills/ui-ux-pro-max
python scripts/search.py "<product type> <industry> <mood keywords>" --design-system -f markdown -p "<Название>" > "E:/Claude/vasya/сайты/<slug>/брифы/pro-max-1.md"
```

Запускаешь **два раза** с разными словами настроения (это два варианта стиля для шага 2).
Дополнительно по необходимости:

```bash
python scripts/search.py "<niche> <mood>" --domain color -n 5
python scripts/search.py "<mood>" --domain typography -n 5
python scripts/search.py "hero social-proof cta" --domain landing -n 5
python scripts/search.py "form validation accessibility" --domain ux -n 8
python scripts/search.py "<keyword>" --stack html-tailwind      # только за UX-правилами, не за Tailwind
```

Что **берёшь** из выдачи: стиль-кандидат, палитру-кандидат, пару шрифтов-кандидат, идеи
для порядка блоков (сверяешь с утверждённой структурой, не заменяешь её), UX-правила,
Pre-Delivery Checklist.

Что **не берёшь**:

- `--persist` (пишет `design-system/MASTER.md` — второй источник правды, конфликт с `DESIGN.md`).
- GSAP-сниппеты и флаг `--motion` — движение не зона Pro Max.
- «Key Effects» с длительностями 400–600 мс — см. этап E.
- Цвета как есть (там бывают чистые `#FFFFFF`/`#000000`) — см. этап C.
- Названия шрифтов как есть (база иногда называет Satoshi / General Sans, а ссылку даёт на DM Sans; и не проверяет кириллицу) — см. этап C.

Сырые выдачи лежат в `брифы/`. Это черновики. Источником правды они не становятся никогда.

## Этап C. Законы (Impeccable) → `DESIGN.md`

Кандидатов из этапа B прогоняешь через `SKILL.md` impeccable, раздел «Shared design laws»,
и `reference/brand.md` (регистр brand). Пишешь `DESIGN.md` по `шаблоны/DESIGN.md`.

Порядок фильтра:

1. **Запреты (absolute bans).** Стиль-кандидат «Glassmorphism», «Liquid Glass», «gradient
   text», «side-stripe borders», «hero-metric», «одинаковая сетка карточек с иконкой» —
   отклоняешь и берёшь следующего кандидата или перезапускаешь этап B с другими словами.
2. **Стратегия цвета.** Выбираешь одну: Restrained / Committed / Full palette / Drenched.
   Для продающего сайта по умолчанию Committed (один цвет несёт 30–60 % поверхности).
   Restrained — если пользователь просил «спокойно, минимализм».
3. **Тема через сцену.** Одно предложение: кто, где, при каком свете, в каком настроении
   смотрит сайт. Оно и решает, светлый или тёмный. Не «ниша → цвет».
4. **Цвета в OKLCH.** Хексы из Pro Max переводишь в OKLCH. Чистых `#000` и `#fff` нет:
   каждую нейтраль подкрашиваешь в сторону бренда (chroma 0.005–0.01). Контраст текста
   ≥ 4.5:1, кнопок ≥ 3:1. В frontmatter `DESIGN.md` кладёшь hex (для совместимости),
   в теле — OKLCH как канон; CSS-переменные пишешь в OKLCH.
5. **Шрифты.** Пару из Pro Max проверяешь: (а) есть на Google Fonts, (б) есть кириллица.
   Подключаешь **не ссылкой на Google**, а локально: `python fonts.py <slug> "Manrope:wght@600;700"`
   → `assets/fonts/fonts.css` (152-ФЗ, см. `право.md`).
   Нет — заменяешь на ближайший по характеру из списка в `SKILL.md` Васи. Шкала заголовков
   с шагом ≥ 1.25, длина строки текста 65–75 символов, запасной системный шрифт в стеке.
6. **Проверка «угадывается по категории».** Первый порядок: если по нише угадывается тема и
   палитра («яхты → синий + белый», «финансы → тёмно-синий + золото») — переделываешь.
   Второй порядок: если угадывается и «нишевая» альтернатива — тоже переделываешь.
   Пожелание пользователя это правило не отменяет: если он сам просил синий, берёшь синий,
   но ищешь необычный оттенок и сочетание.
7. **Referens-сайты пользователя.** Что в них нравится, переносишь как приёмы (сетка,
   плотность, характер шрифта, ритм отступов), а не как копию. Анти-примеры — в
   `Do's and Don'ts`.

Результат: `DESIGN.md` с frontmatter-токенами (colors, typography, rounded, spacing,
components) и шестью разделами в фиксированном порядке: Overview, Colors, Typography,
Elevation, Components, Do's and Don'ts. Движение сюда **не** пишешь (см. этап E; заметки
о движении — в `Do's and Don'ts` одной строкой со ссылкой на этап E).

Проверка: `load-context.mjs` показывает `hasDesign: true`.

## Этап D. Сборка (Impeccable как свод законов)

Собираешь `site/index.html`, `styles.css`, `script.js` по утверждённой `структура.md` и
`DESIGN.md`. Перед кодом читаешь из impeccable: `reference/brand.md`,
`reference/typography.md`, `reference/spatial-design.md`, `reference/responsive-design.md`,
`reference/ux-writing.md`. Для формы — `reference/interaction-design.md`.

Гейты impeccable (`teach`, `shape`, image probes, north-star mock) **не запускаешь**: их
роль уже выполнили Васино интервью и утверждённая структура. Для порядка фиксируешь в
отчёте строку:

```
IMPECCABLE_PREFLIGHT: context=pass product=pass command_reference=pass shape=pass(структура утверждена пользователем) image_gate=skipped:статический сайт по утверждённому DESIGN.md mutation=open
```

Правила сборки поверх законов impeccable:

- Семантика: `header / main / section / footer`, один `h1`, заголовки по порядку, `button`
  для действий, `a` для переходов, `label` у каждого поля.
- CSS-переменные из `DESIGN.md`, никаких «голых» цветов в стилях.
- Отступы — из шкалы `spacing`, ритм разный между блоками (одинаковый паддинг везде — монотонность).
- Карточки — только там, где это лучшее решение; вложенных карточек нет.
- Копирайт: каждое слово работает; заголовок блока не повторяет вводный абзац. Тире «—»
  только по правилам русской пунктуации, не как декоративный разделитель в списках и
  заголовках (запрет impeccable на em-dash написан для английского UI-копирайта).
- Кнопка целевого действия: один цвет, один текст-глагол по всему сайту, в hero + середине + конце.
- Тап-цели ≥ 44 px, фокус видимый, контраст по `DESIGN.md`.

## Этап E. Движение (Design Motion Principles, режим Create)

Единственная библиотека, которая решает, что и как двигается. Читаешь
`workflows/create.md`, `references/motion-cookbook.md`, `references/accessibility.md`,
`references/creation-gotchas.md`. Взвешивание для продающего сайта по таблице скилла:
**Jakub — основной, Jhey — второстепенный, Emil — для форм и навигации.** Если пользователь
просил «спокойно, по-деловому» — Emil основной. Для магазина (таблица скилла, строка
E-commerce): **Jakub — основной, Emil — второстепенный, Jhey — только показ товара**
(галерея, добавление в корзину). Админка — **Emil основной**: частые действия, движения
почти нет. Взвешивание объявляешь в отчёте одной
строкой, пользователя об этом не спрашиваешь.

Правила:

- **Частотный гейт Эмиля** перед каждой анимацией: hover/press у кнопок — 120–200 мс;
  появление блоков при скролле — один раз, 250–400 мс, `opacity + translateY` до 12 px;
  навигация, фокус, ввод в форму — без анимации.
- Только `transform`, `opacity`, `filter`. Никогда `width/height/top/left`.
- Изинг: `cubic-bezier` ease-out-quart/quint/expo. Без bounce и elastic. Без `ease` по умолчанию.
- `@media (prefers-reduced-motion: reduce)` отключает всё движение — в том же файле, не потом.
- Без scroll-jacking, параллакса на мобильном, автопрокрутки, зацикленных «дышащих» градиентов.
- Библиотек нет: CSS-transitions, `@keyframes`, `IntersectionObserver` для появления.
